# 边界与错误处理

根据实际命令选择相关分支，不要求每个流程实现所有策略。

| 观察到的操作 | 需要确定的选择 | 应询问的示例 |
| --- | --- | --- |
| Git 更新 | 本地改动、分叉时如何处理 | “本地有改动或历史分叉时，停止并提示，还是采用你指定的同步方式？” |
| 手机投屏或外设 | 目标设备、未连接时的处理、等待期限 | “手机未连接时立即结束，还是等待？若等待，最长多久？” |
| 本地服务 | 已有监听进程时复用、退出还是另开端口 | “目标端口已占用时应该跳过，还是改用指定端口？” |
| 网络下载或同步 | 可重试阶段、重试上限、认证交互 | “启动时联网失败，应结束还是重试？若重试，最多几次？” |
| 删除、覆盖、上传、推送 | 数据范围、重跑及失败后的状态 | 就缺失的操作目标或恢复策略提出具体问题 |

用户已经给出策略时不重复询问。只因操作可能失败，不必额外引入重试、后台守护、日志系统或自动修复。风险更低且不影响结果的实现细节由代理自行决定。

## 脚本行为

- 前置条件不满足时，在相应阶段报错；关键命令失败后不执行依赖该结果的步骤。
- 区分“资源缺失”“资源未授权”“进程退出失败”等已能确定的情况；未确定原因时给出实际退出码和诊断动作，不猜测根因。
- 等待应有可执行的截止条件。外部检查命令自身可能阻塞时，也需设置其调用超时；不能仅给循环设置截止时间。
- 重试前判断是否已产生副作用。将只读检查与写入步骤拆开，避免重复上传、创建或提交。
- 只清理由当前脚本创建且已确定归属的临时文件或进程。已有服务的终止、系统设置变更按用户明确选择执行。
- 交互式认证需要用户在场；登录自启若依赖已保存凭据，应明确这一前置条件。凭据通过现有凭据存储或环境变量读取，不复制到脚本、错误提示或测试输出。

## 文案

错误包含阶段、已知原因和下一步。例如“连接设备 fb5d62a6 超时（120 秒），请连接 USB 并允许调试后重试”。字段提示使用“工作目录”“标签页颜色”等直接名称。

只为已出现或已明确适用的失败条件写提示。保留外部程序的相关错误输出，避免仅返回“执行失败”，也不要以“成功”覆盖前面的错误。

## 验证场景

围绕当前脚本挑选能观察行为的测试：命令成功；依赖缺失；关键命令非零退出且后续步骤未运行；选定的超时或重复启动策略。对网络请求使用模拟服务，对 Git 使用临时本地仓库，对设备使用模拟命令验证分支，再在具备设备时做真实联调。
